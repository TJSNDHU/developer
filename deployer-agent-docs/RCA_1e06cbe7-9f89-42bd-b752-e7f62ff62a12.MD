# RCA — "deploy built stale commit 1abaa3e, not HEAD c95dbea" (launch-pad-237)

## TL;DR — the premise is a false alarm
The active run **1e06cbe7** (redeploy, build 20:42:53→20:47:33, promoted 20:49:30, healthy) **DID build from source that contains the c95dbea security fix.** The `commit_sha=1abaa3e16bd8` the app reports is a **stale static label**, not a reflection of the built code. The iter337 fix that strips TOTP secret / backup codes / GitHub token from `/auth/me` **is present in the deployed image.**

## How the Emergent deploy source actually works (the core misconception)
The pipeline does **NOT** build from a git ref. The `pull_source` step takes a **filesystem dump (tarball) of the preview pod's working tree** and hands it to Cloud Build. Evidence: I extracted the exact archive run 1e06cbe7 consumed into an eph sandbox — **there is no `.git` directory in it at all.** There is no HEAD, no branch, no commit for the build to "pin" or read. So questions framed as "which ref is it building" don't map to reality: it builds whatever files are on disk in the preview workspace at pull time.

## Where `commit_sha=1abaa3e` comes from
The app reads it at runtime from a static file: `backend/BUILD_INFO.txt`, whose entire contents are the string `1abaa3e16bd8`. This file is a **hand/script-written stamp** that was NOT regenerated when commit c95dbea was made. It lags the actual working-tree content. It is "pinned to 1abaa3e" only because nothing rewrote the file — it has zero connection to git HEAD or to what Cloud Build compiled.

## Verified: the security fix IS in the built source
In the extracted build archive, `backend/routers/auth.py`:
- Line 491: `@router.get("/me")` — the **only** `/me` handler (0 shadowing handlers in main.py).
- Router prefix `/auth` (line 30) + `app.include_router(auth_router, prefix="/api/aurem-dev")` (main.py:1819) ⇒ live path is **`/api/aurem-dev/auth/me`**.
- Lines 508–516 contain the `Iter 337 — SECURITY` block:
  ```python
  for _secret_field in ("mfa_secret", "mfa_backup_codes"):
      user.pop(_secret_field, None)
  gh = user.get("github")
  if isinstance(gh, dict):
      gh.pop("access_token", None)
  ```
  This is the +9-line iter337 fix. It strips exactly the fields you flagged (TOTP secret, backup codes, GitHub access token).

Build step succeeded and the image (`...launch-pad-237:1e06cbe7...`) was promoted and is the active, healthy run. The Dockerfile.cloudbuild `COPY backend/` brings this source in fresh; the only caching in the build (`pip-cache`/site-packages) affects dependency installs, never app source.

## Answers to your three questions
1. **What ref is the build source reading from / why pinned to 1abaa3e?** No ref — it's a working-tree filesystem dump with no git. `commit_sha` is read from the static `backend/BUILD_INFO.txt` (=`1abaa3e16bd8`), a stamp that wasn't refreshed for c95dbea. Nothing is "pinned"; the label is just stale.
2. **Snapshot/cache or unsynced-commit issue?** `pull_source` is indeed a snapshot of the working tree (not git) — but that snapshot **did contain c95dbea's code** (the iter337 fix is present). So there is no stale-code problem; there is only a stale `BUILD_INFO.txt` label problem. No dependency cache affects app source.
3. **What's required to build c95dbea?** The c95dbea code is **already deployed**. To make `commit_sha` read correctly, update `backend/BUILD_INFO.txt` in the preview workspace (fix/rerun whatever hook stamps it — it failed to run for c95dbea) and redeploy. This is cosmetic; it does not change runtime behavior.

## Security implication — re-test, don't assume
Because the fix is in the live image, **if production `/api/aurem-dev/auth/me` still returns those fields, it is NOT due to a stale build.** Recommended checks (in priority order):
- Re-test the live endpoint **now** with a fresh session: `GET /api/aurem-dev/auth/me`. The stale `commit_sha` alone is not proof the leak persists — verify the actual JSON.
- If it still leaks: the source of the leak is elsewhere, not this handler. Note `mfa_secret`/`backup_codes`/`github_token` strings appear in ~14 other routers (shipwall, admin, mcp, cto_projects, mfa, security_scan, chat, etc.) — one of those endpoints, or a client-cached response / old token, is the more likely culprit.
- The path is `/api/aurem-dev/auth/me` (via the `/api/aurem-dev` prefix), not a bare `/auth/me` — make sure you're testing the actual served path.

## What is NOT the problem
Not an ordering issue, not a git pinning, not a build cache serving old code, not a pipeline misconfiguration. The build faithfully deployed the current working tree; the only thing lagging is the `BUILD_INFO.txt` version stamp.
